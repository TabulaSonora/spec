# Supporting more than one `SCCore.dll` build

Everything else in this repo is pinned to a single `SCCore.dll` — the 2019-10-30 x64 build (see
[`DLL_LAYOUT.md`](DLL_LAYOUT.md) and [`PROVENANCE.md`](PROVENANCE.md) §0). Roland shipped several
builds of SOUND Canvas VA, and users have whichever one their installer gave them. This document is
the survey that has to come before multi-version support: **what actually changes between builds, what
does not, and therefore what a version-aware loader has to do.**

The three builds examined so far are registered in
[`../tables/versions.json`](../tables/versions.json), regenerated by
[`../tools/identify_dll.py`](../tools/identify_dll.py). All three live untracked at the
`TabulaSonora` repo root — `SCCore.dll` (2019 x64, the pinned build), `SCCore.64.dll` and
`SCCore.32.dll` (the 2016 pair). Point tooling there, not at a download directory.

---

## 1. Identifying a build

**No SC-VA build carries a version number.** All three have an empty `VS_VERSION_INFO` — in fact
their `.rsrc` holds *only* the boilerplate `asInvoker` trustInfo manifest, nothing else. There are no
`FileVersion`, `ProductName`, or `LegalCopyright` fields, and no version string anywhere in the image.
The GS identity strings (`Roland SC-GS    Version 1.00` / `1.10`, `Roland XP-GS    Ver.1.01`) are
byte-identical in all three builds: they are the emulated *hardware* firmware's identity, not the
product's, so they cannot distinguish builds either.

A build must therefore be identified by **SHA-256**, with size and PE timestamp as corroboration.

| | **2016-03-09 x86** | **2016-03-09 x64** | **2019-10-30 x64** (pinned) |
|---|---|---|---|
| size | 27,472,384 | 27,440,128 | 27,347,456 |
| SHA-256 | `8ddb29d5…244f29` | `e95e7f8f…268c47` | `117e6aa1…20bdb1` |
| MD5 | `d44d1b8c9a6f956ca2324f2f5d348c44` | `f16b5eb9c7e204de7f9b3a829d2d5500` | `dbd9a30c168efef577d40a28d9adf37d` |
| PE timestamp | `1457503331` → 2016-03-09 06:02:11 UTC | `1457503232` → 2016-03-09 06:00:32 UTC | `1572416468` → 2019-10-30 06:21:08 UTC |
| machine | x86 (`0x014c`) | x64 (`0x8664`) | x64 (`0x8664`) |
| image base | `0x10000000` | `0x180000000` | `0x180000000` |
| MSVC linker | 10.0 (VS2010 SP1, `Rich` build 40219) | 10.0 (VS2010 SP1, `Rich` build 40219) | 14.16 (VS2017 15.9, `Rich` build 27031) |
| sections | `.text .rdata .data .rsrc .reloc` | `.text .rdata .data .pdata .rsrc .reloc` | `.text .rdata .data .pdata .rsrc .reloc` |

The two 2016 files are **the same release built for two architectures**, not two releases: their PE
timestamps are 99 seconds apart, they share an identical `Rich` header toolchain fingerprint, and
their data payloads match (the tone table and patch directory are byte-identical between them at a
constant `0x7e00` skew). Treat `2016-03-09-x86` and `2016-03-09-x64` as one *version* with two
*images*.

Full hashes are in [`../tables/versions.json`](../tables/versions.json).

## 2. What is stable across builds

This is the good news, and it is most of the value.

### The exported ABI is identical

All three export the same **17 `TG_*` functions**, same names, same ordinal base:

```
TG_LongMidiIn  TG_PMidiIn  TG_Process  TG_ShortMidiIn  TG_XPgetCurSystemConfig
TG_XPgetCurTotalRunningVoices  TG_XPsetSystemConfig  TG_activate  TG_deactivate
TG_flushMidi  TG_getErrorStrings  TG_initialize  TG_isFatalError
TG_setInterruptThreadIdAtThisTime  TG_setMaxBlockSize  TG_setSampleRate  TG_terminate
```

So anything that *drives* the DLL rather than reading data out of it — notably the `scdec` oracle
harness in [`../tools/decoder/`](../tools/decoder) — is version-independent by construction. The one
caveat is bitness: the 2016 x86 image needs a 32-bit host process, so `scdec` must be published `win-x86`
to load it.

### The wave ROM is bit-identical — only its *layout* moved

All three embed the same 24 MB of wave data: 24 self-identifying 1 MB blocks, the same three hardware
generations with the same original ROM build stamps (`ver200` 1994-12-08 / `rom_make` 1996-06-16 /
`8820_wv0` 1999-08-17), and the same two bank blobs — **16 MB + 8 MB, byte-for-byte equal between 2016
and 2019.** These are the SC-8820's two physical mask ROMs (IC7 / IC39, see
[`HARDWARE_ROMS.md`](HARDWARE_ROMS.md)); neither chip image changed.

What changed is the order the two blobs are stored in the file:

| build | first blob | second blob |
|---|---|---|
| 2019-10-30 x64 | `0x92700` — 16 MB (`ver200` ×8 + `rom_make` ×8) | `0x1092730` — 8 MB (`rom_make` ×4 + `8820_wv0` ×4) |
| 2016-03-09 x64 | `0x215120` — 8 MB (`rom_make` ×4 + `8820_wv0` ×4) | `0xa15130` — 16 MB (`ver200` ×8 + `rom_make` ×8) |
| 2016-03-09 x86 | `0x20cd48` — 8 MB | `0xa0cd58` — 16 MB |

The 2019 build stores the banks in generation order; the 2016 builds store the 8 MB bank first. The
`+0x30` file-layout drift that DLL_LAYOUT notes at the 2019 block-15→16 boundary is the seam between
the two blobs — in the 2016 builds the same seam appears as a `+0x10` drift at the 8 MB/16 MB
boundary. Same two chip images either way.

**Implication:** a loader should never hard-code the ROM base. Scan for the block magic
(`A4 EB A5 2B E9 29` at each 1 MB block head), group the hits into maximal runs of consecutive blocks,
and identify each bank by its size and generation labels. `identify_dll.py` does exactly this and
recovers the banks correctly on all three builds without being told anything about them.

### Most of the patch directory is unchanged

`g_tone_table` (604,928 B), `g_wavedesc_table` (93,698 B) and `g_layered_table` (1,200 B) are
**byte-identical** across 2016 and 2019 — the tone definitions, wave descriptors and alternate-
articulation table did not change. `g_multisample_table` matches for its first 164,500 bytes and then
continues at a different shift — a re-packing, not a revision (§5.1). Rendering through both DLLs
confirms the zone map behaves identically.

## 3. What is *not* stable: every offset

There is no usable relationship between the builds' offsets. Tables were not merely shifted by a
section delta — they were **reordered**. Comparing the 2019 and 2016 x64 positions of tables that are
byte-identical in both:

| table | 2019 x64 | 2016 x64 | delta |
|---|---|---|---|
| `g_lfo_delay_tbl` | `0x19a1590` | `0x105140` | `0x189c450` |
| `g_lfo_cents_tbl` | `0x19a1690` | `0x104f40` | `0x189c750` |
| `g_lfo_rate_tbl` | `0x19a1790` | `0x105040` | `0x189c750` |
| `g_level_curve` | `0x19a1a00` | `0x104900` | `0x189d100` |
| `g_amp_curve_hi` | `0x19a1ba0` | `0x104a00` | `0x189d1a0` |
| `g_rate_curve` | `0x19a1900` | `0x104260` | `0x189d6a0` |
| `g_pan_tbl` | `0x19a1fa1` | `0x104841` | `0x189d760` |

Six different deltas among seven tables, and the *relative order* differs too: in 2019 the LFO
tables run delay → cents → rate; in 2016 they run cents → rate → delay. Any scheme that tries to
project the pinned offsets onto another build with a per-section constant will silently read the
wrong table.

**Offsets must be derived per build, never translated.**

## 4. What has to be re-derived per build

Running the pinned build's 52 cached tables against each 2016 image by byte-exact content search:

| build | located byte-exact | unresolved |
|---|---|---|
| 2016-03-09 x64 | 26 / 52 | 26 |
| 2016-03-09 x86 | 26 / 52 | 26 |
| 2019-10-30 x64 | 52 / 52 | 0 (self-check) |

The 26 located tables — with their per-build offsets — are listed under each build's `tables` key in
[`../tables/versions.json`](../tables/versions.json). They cover the TVA amplitude/level curves, the
envelope segment-rate curve and shape table, the LFO rate/cents/delay tables and waveform map, the
TVF cutoff/Q/warp/ceiling tables, the SVF exp and f-ceiling tables, the resample kernel, the pan
table, portamento step, the tone/wavedesc/layered directory tables, and the two tone-indirect banks.

The other 26 fall into two groups, and the distinction matters:

**(a) Blobs that overlap each other in the file.** The eight `kf_*` key-follow blobs are 16 KB–32 KB
windows spaced only `0x80`–`0x300` apart, and `lut2` (16 KB) and `lut3` (64 KB) start `0xa00` apart.
It is tempting to read that as an extraction error. It is not: these symbols are **base pointers into
a shared region**, and each one really does span its own whole indexable range — `g_kf_tvalevel` is
read as `block[0x54]*0x80 + key`, and `block[0x54]` reaches `0x7f` across the tone table, so all 128
rows (16 KB) are reachable from that base. The overlap is how the data is actually laid out. Each
entry in `manifest.json` now carries the `index` expression and `rows` count that bounds it; **do not
shrink one of these blobs to the next entry's offset.**

What *does* break cross-build matching here is that a 16 KB window fails as soon as anything anywhere
inside it moves, which for a shared region is almost guaranteed.

The one genuine over-read was **`kf_tvfenv`**, and it is genuine because the index is *masked*:
`(block[0x32] & 0xf)*0x80 + key` cannot reach past row 15, so as an `s16` table it is 16 × 128 × 2 =
**4096 bytes**, not the 32768 the manifest claimed. That is now fixed and the cached `.bin`
regenerated. A masked index is the only sound basis for shrinking one of these: an *observed* range
is not enough, because a value absent from the tone table can still be written at runtime by SysEx.

*A finding in the other direction.* `g_kf_pitchrate0` and `g_kf_pitchrate1` are indexed
`block[0x27]*0x80 + key`, and `block[0x27]` reaches `0xff` in the tone table — row 255, which is
outside the 16 KB these blobs cover. Those two are **under-read**, and the Python engine would raise
on any voice that reached there. Left as-is and flagged in the manifest rather than silently widened,
since establishing whether the DLL clamps `block[0x27]` needs a look at the decompile.

**(b) Short ramp-like curves that are not byte-identical anywhere in the 2016 image.** These are
voice-shaping curves, and whether their data changed or the blob extents are simply wrong for them
matters audibly.

> ⚠️ **Do not locate either group by fuzzy content search.** They are short monotonic ramps, and
> `.rdata` is full of other short monotonic ramps. Prefix search, interior-window search and
> chunk-voting all return confident, *wrong* answers: chunk-voting places `g_reso_curve` at 2016
> `0x1049e8` with 84 % byte agreement, while element-wise the pinned table reads `0, 26, 52, 77,
> 103, …` (ascending) and the bytes there read `1225, 1109, 994, 880, 767, …` (descending).
> `identify_dll.py` reports byte-exact hits only and lists everything else as unresolved.

## 5. The code cross-reference pass

Content search is the wrong tool for group (b); the code is the stable thing. The same source
compiled twice puts the instruction that indexes a table at the same point of the same function, so
matching *functions* across two builds locates the tables as a by-product.
[`../tools/ghidra_scripts/DumpXrefs.java`](../tools/ghidra_scripts/DumpXrefs.java) dumps every
function's ordered data references and call targets, and
[`../tools/match_xrefs.py`](../tools/match_xrefs.py) diffs two such dumps:

1. **seed** — exported and CRT symbol names (all three builds keep the 17 `TG_*` exports), plus
   anchor tables referenced by exactly one function in each build
2. **propagate** — matched functions' call sites align by order, matching their neighbours
3. **refine** — match functions whose (anchor tables, matched callers, matched callees) fingerprint
   is identical and unique on both sides
4. **rank** — best-match the remainder on data-reference mnemonic sequence plus matched-neighbour
   context, accepted only with a margin over the runner-up
5. **vote** — align each matched pair's reference sequences and read the wanted table's slot

Steps 2–4 iterate to a fixpoint. Against the 2016 x64 image this matches **538 of the pinned build's
1047 functions**.

Voting is by *range*, not by base address: a table is indexed at many offsets — `g_rate_curve` alone
has sixteen reference sites, most of them partway in — so any aligned reference landing inside the
reference build's table votes for `target_va − (ref_va − table_va)`. Counting only exact-base
references discards nearly all the evidence and roughly halves the yield.

### Corroboration, and one test that looked sound but was not

Cross-referencing alone is not trustworthy enough to publish. Cross-validated against the 26 anchors
— locating each by cross-reference as if it were unknown, then checking against what content search
already proved — it answers for only 8 of 26 and gets 7 of those right. **88 % precision at 31 %
recall is a lead, not a fact.**

The obvious corroboration is the **x86/x64 pair**: Roland shipped each release as two images built
minutes apart from one source, and their table data is identical. The tempting test — *take the
candidate's bytes from one image and check they reappear in the other* — is **worthless**, and this
document previously relied on it. The two images of a release are near-copies of each other, so
almost anything passes: sampling 200 arbitrary 2 KB windows of the 2016 x64 `.rdata`, **199 reappear
verbatim in the x86 image**. A test that accepts ~100 % of random inputs confirms nothing, and four
offsets it "confirmed" were later shown wrong.

The sound version searches with the **pinned build's** bytes, twice and independently:

1. **vote** — slide several distinct windows of the pinned blob across image A; each window matching
   *uniquely* votes for `hit − window_offset`. Independent windows agreeing on one base is what rules
   out a ramp collision.
2. **repeat** — do it again, independently, against image B.
3. **check** — the two bases must differ by roughly the shift the *neighbouring* anchors show.

Step 3 carries the weight, and only because each search was driven by pinned-build content that
neither 2016 image contains at an arbitrary offset. This is [`../tools/hunt_tables.py`](../tools/hunt_tables.py).

### Result, and what the oracle said about it

Locating tables by content voting produced a table of partial matches — `g_vel_curve` 142/256 bytes,
`g_env_rate_out` 539/1024, `g_multisample_table` 186323/286720 — which I read as *the 2016 release is
a different voicing*. **That was wrong.** The A/B below falsified it, and it is worth being precise
about why, because the mistake is easy to repeat.

### The A/B test — the only thing that settled it

`scdec` drives the real DLL through its exported API, so the two builds can be rendered against each
other directly. Under CrossOver's ARM-Windows bottle (FEX executes the x86-64 code) the harness runs
unmodified; only `holdnote` and the other pure-API modes are usable, because the memory-peeking modes
hardcode `DAT_181a1b570`, which is a *pinned-build* address — point them at another build and they
read strings out of the middle of `.rdata`.

100 cases, one note per process (GS Reset leaves state behind, so a batch cannot be trusted),
identical event streams, 32 kHz, reverb and chorus off:

- 10 GM programs × 3 octaves × 2 velocities — envelopes, key-follow, multisample zones
- 10 synth patches × banks 0/8 × velocities 1/127 — resonant filters and the LFO wavetables

**All 100 essentially identical. Maximum deviation exactly 1 LSB of 16-bit, relative RMS ~1e-5**, and
never 2 LSB in any case. That is the signature of arithmetic rounding, not of different data — a real
table difference would show up as a large deviation in at least some patches.

**The two 64-bit builds are behaviourally equivalent.** The residual is the MSVC 10.0 → 14.16
toolchain change.

### 5.1 The tables were re-packed, not retuned

If the data is the same, why did whole-blob searches fail for half the tables? Because **`.rdata` was
re-packed into differently ordered segments**, and the cached blobs span segment boundaries.

Walking a blob forward through the 2016 image shows it directly. `g_kf_tvalevel` matches exactly for
896 bytes at `0xa5810`, then its continuation reappears at `0xa4110` (3584 bytes), then at `0xa5210`
(256 bytes). The *same* 2016 segments — `0xa4110`/3584, `0xa5210`/256, `0xa5890`/768, `0xa5b90`/896 —
recur while walking `g_kf_tvalevel2`, `g_kf_tvarate0`, `g_kf_tvarate1` and `g_kf_tvfenv`, which is
exactly what one shared region re-ordered under overlapping windows looks like.

So a short exact run means **a segment boundary, not a data change**. Every "partial match" figure in
the earlier draft of this document was measuring where the pinned blob crossed into a segment that
moved somewhere else.

Three method lessons, each paid for:

- **Whole-blob search is the wrong primitive** when blobs are over-reads spanning re-packed segments.
  Exact-*prefix* search is right: it is anchored at the table's own start.
- **Interior-window voting is actively wrong** in a shared region. A window drawn from one blob may be
  bytes belonging to a neighbouring table, so the vote confidently returns a coherent but wrong base.
  It put `g_kf_tvalevel` at `0xa3d90`; prefix matching and the oracle put it at `0xa5810`.
- **Only the oracle is decisive.** Three static methods (content search, code cross-reference, window
  voting) agreed with each other on several offsets that the render test then disproved.

### Where the tables are: a segment map, not a table map

Because the re-packing splits tables, the durable artefact is a **piecewise offset map** rather than a
per-table address list. [`../tools/segment_map.py`](../tools/segment_map.py) indexes the target's
non-ROM `.rdata`+`.data`, slides a window across the pinned build's table area, merges runs sharing a
shift into segments, then closes the leftover gaps by testing neighbouring shifts and accepting only
on exact byte equality. (Gaps appear because common data — linear ramps like `80 82 84 86 …` — occurs
in many places, so no window anchors it. Ambiguous, not absent.)

| | segments | distinct shifts | table area mapped | bytes verified byte-equal |
|---|---|---|---|---|
| 2016-03-09 x64 | 824 | 701 | 97 % | **1,153,300 — all match** |
| 2016-03-09 x86 | 801 | 751 | 97 % | **1,150,763 — all match** |

The verification is the point: every table was reassembled out of the 2016 image through the map and
compared against the pinned bytes, and **every mapped byte is identical, with zero mismatches**. That
is independent confirmation of what the render A/B showed — same data, different packing.

The maps ship as [`../tables/segments-2016-03-09-x64.json`](../tables/segments-2016-03-09-x64.json)
and [`-x86.json`](../tables/segments-2016-03-09-x86.json); `versions.json` links them per build and
records per-table coverage.

**39 of 52 tables fully resolved** in each image. Every one of the eleven that no per-table search
could place is now covered, most completely:

| symbol | pieces | coverage | first piece (x64) |
|---|---|---|---|
| `g_pitch_env` | 4 | 100 % | `0xf4bb8` |
| `g_reso_curve` | 3 | 100 % | `0x1047e8` |
| `g_env_scale_curve` | 2 | 100 % | `0xf2cf8` |
| `g_pitch_depth_vs` | 3 | 100 % | `0xf2e28` |
| `g_env_startphase` | 4 | 100 % | `0xff790` |
| `g_filter_type_coef` | 4 | 100 % | `0x11ddd8` |
| `g_vel_sens` / `g_vel_xfade` | 3 each | 100 % | `0xa3b90` / `0xa3590` |
| `g_kf_pitchrate0/1`, `g_kf_tvfrate` | ~32 each | 13–59 % | fragmented |

`g_reso_curve` deserves a note: the previous draft flagged it as possibly rescaled and inverted
(0..1225 descending against the pinned 0..258 ascending). It is neither — it resolves at 100 % and is
byte-identical. That reading came from a base that was one table off, exactly as the A/B implied.

The thirteen still partial are almost all the **`kf_*` over-read windows** — 16 KB blobs that span far
past any real table, so a large share of what they cover is unrelated data (§4). Their actual
key-follow rows are covered. The rest (`g_multisample_table` 99 %, `g_dir_lut3` 99 %,
`g_lfo_wavebank` 94 %, `g_lfo_wave` 84 %) lose only ambiguous runs.

## 6. What multi-version support should look like

The survey points to one design. **Stop treating "the DLL" as a pinned constant with known offsets,
and treat it as an image to be probed.**

1. **Fingerprint on load.** SHA-256 the image, look it up in `tables/versions.json`. A known build
   yields its table map directly. Refusing to run on an unknown build (what `extract_tables.py` does
   today) stays the right default for correctness-critical paths.
2. **Discover, don't assume, the wave ROM.** Scan the block magic and group by contiguity, per §2.
   This already works on every build tested and needs no per-version data.
3. **Content-locate the stable tables.** The 26 that are byte-identical need no per-build work beyond
   the search `identify_dll.py` already does — a new build is onboarded automatically for that half.
   Then run `segment_map.py` for the rest: it maps the whole table area piecewise and verifies every
   segment byte-for-byte, which is stronger than any per-table guess and needs no Ghidra.
4. **Dual-image vote for the rest**, per §5 — `hunt_tables.py` needs no Ghidra and resolves 21 of the
   26 the exact search misses. Fall back to cross-referencing only for what it cannot place. A new
   release that ships an x86/x64 pair is cheap to onboard; a single-image release is not, because the
   corroborating step is gone.
5. **Bound every table by its indexing expression, not by its neighbour.** `manifest.json` now
   records `index` and `rows` for the shared-region tables, which is what makes an extent defensible.
6. **Verify against the DLL, not against the pinned offsets — and do it early.** This is not the last
   step, it is the referee. Three static methods agreed on offsets the render test then disproved
   (§5.1). One note per DLL instance; the pure-API modes (`holdnote`, `seq`, `song`, `notebatch`) are
   the portable ones, since every memory-peeking mode hardcodes pinned-build addresses.

The practical position: **a 2016 build can be driven as an oracle today** (the ABI is identical), its
wave ROM and patch directory read correctly, the whole table area is mapped byte-verified onto it, and the render output matches the pinned build to within 1 LSB. What it
cannot yet do is feed the reimplementation a complete table set.

## 7. Reproducing this survey

Fingerprint any build and content-locate what it can:

```
python tools/identify_dll.py /path/to/SCCore.dll [more.dll ...] [--json out.json]
```

Run against the pinned build it reports 52/52, which is the tool's own self-check.

For the cross-reference pass, dump xrefs from each build with Ghidra headless, then diff them:

```
analyzeHeadless <proj> scva -import SCCore.dll -overwrite \
    -scriptPath tools/ghidra_scripts \
    -preScript  TuneAnalysis.java \
    -postScript DefineTableFunctions.java \
    -postScript DumpXrefs.java out/xrefs.json

python tools/match_xrefs.py  pinned.json  SCCore.dll \
                             target.json  SCCore.64.dll \
                             --sibling SCCore.32.dll --json match.json
```

Both need no Ghidra:

```
python tools/hunt_tables.py  SCCore.dll  SCCore.64.dll  SCCore.32.dll  --json hunt.json
```

```
python tools/segment_map.py  SCCore.dll  SCCore.64.dll  --json segments.json
```

`segment_map.py` is the one that actually resolves the fragmented tables — it builds the piecewise map
of §5.2 and verifies every segment. It takes about four minutes per image.

`hunt_tables.py` takes the pinned build plus **both images of the release being onboarded**, and does
the dual-image vote of §5. Treat its output as leads: §5.1 shows interior-window voting returns
confident wrong answers inside a re-packed shared region. Prefer exact-prefix hits, and settle
anything that matters with the A/B below.

### The A/B render test

```
WINE="/Applications/CrossOver Preview.app/Contents/SharedSupport/CrossOver/bin/wine"
"$WINE" --bottle <bottle> --workdir "$PWD" 'Z:\...\publish\scdec.exe' \
        'Y:\path\to\SCCore.dll' holdnote <program> <note> <hold_s> out.wav <vel> [bankMSB]
```

One invocation per note — GS Reset leaves state behind, so a batch in one process is not trustworthy.
Render the same event stream through both builds and difference the WAVs. On an Apple-Silicon host
this works through CrossOver's ARM-Windows bottle, where FEX executes the x86-64 code; the harness
needs no changes, only a `wine` that resolves the bottle (`--bottle`, *not* `WINEPREFIX`).

`TuneAnalysis.java` keeps auto-analysis off the 24 MB of wave ROM — without it the bulk-data
analyzers spend all their time there. `DefineTableFunctions.java` must run before the dump: much of
the control path is reached only through data pointer tables, so nothing *calls* it and auto-analysis
never disassembles it (it recovers 214 such functions in the pinned build, 225 in the 2016 x64 one).
Analysis takes about 20 seconds per image. Pass `--sibling` whenever the release shipped an x86/x64
pair — without it nothing reaches the `confirmed` grade.
